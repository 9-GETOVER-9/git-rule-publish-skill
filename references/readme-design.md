# README：先有事实，再有版式

在用户要求项目介绍、新公开仓库或 README 已过时时使用。参考排版是居中标题、简明价值主张、真实徽章、引用块、分层正文和折叠详情；不复制别人的能力宣称、数字、署名或许可证。

## 写作前

读取项目入口、版本、安装方式、可运行命令、测试与限制、许可证及现有文档。先确认“谁用、解决什么、第一步怎么做、怎样验证”。事实缺失就省略或明确未知，不能为了首屏饱满编测试数、Star、兼容性或 READY。

已经有清晰 README 时保留其信息架构与团队表达；用户只要小改就小改。尚未运行的命令写为使用方式，不能写成实测；例子输出只能来自实际运行或清楚标为示意。

## 可适配的布局

1. 顶部 `<div align="center">`：项目名、简洁的价值说明、少量有依据的标签或徽章、安装/使用/文档跳转。HTML 块前后留空行，避免里面 Markdown 不渲染。
2. 一段引用块说明适用场景；正文先给能复制的安装/最短使用路径，再讲能力。
3. 功能表只列真实差异；用具体输入/输出示例说明用途。扩展安装方式可放 `<details><summary>…</summary>`，最常用方式默认展开。
4. 根据实际需要加配置、工作流、项目结构、限制、测试与贡献链接。简单项目不强行塞满所有栏目；长细节移到 docs 并给入口。
5. 许可证徽章只有 LICENSE 实际存在且与声明一致时出现；CI 徽章链接真实工作流；版本链接实际版本/Release。Stars 用动态来源，不手填数量。不要标“已认证”“完全安全”或用测试数冒充成功率。

模板入口在 Skill 的 `assets/readme-template.md`，只作布局起点，交付前删除所有占位符。Shields.io 徽章是远程图片，会访问其服务；无外部图片要求时用文字链接。徽章颜色与布局是装饰，不是质量证明。

## GitHub 渲染边界与检查

使用 GitHub 支持的 Markdown 和少量 HTML：标题、表格、引用、代码块、`div align`、`details/summary`。不依赖自定义 CSS、style 属性、script、iframe 或网页 App 才能看到的效果。示例截图里的橙色圈选不在其 README 源码中，不把圈选当成需要复刻的框架。

先运行 `python scripts/check_readme.py --root <项目目录>` 检查本地链接、未替换占位符和不支持的 HTML；它不验证远程链接是否在线，也不能核实所有文字事实。人工检查命令、徽章目标、数字依据、图片替代文本及深浅色可读性。

发布前尽量预览实际 GitHub 渲染；可用仓库预览或 GitHub Markdown API，送出的只能是获准公开的 README，不把私人草稿上传当预览。交付时说明实际预览范围和未核实项。检查通过不会自动赋予推送许可。
